title: "title: \"AKINSOFT WOLVOX Kontrol Panel TCP/3055 — Unauthenticated Database Credential Disclosure\" date: \"2026-10-01\" description: \"WOLVOX Kontrol Panel'in TCP/3055 login akışında, başarısız kimlik doğrulamasına rağmen yapılandırılmış veritabanı yönetici kimlik bilgilerinin yanıta eklenmesi.\" tags: - vulnerability-research - reverse-engineering - windows - delphi - cwe-200 - wolvox --- ## Giriş WOLVOX üzerinde çalışmaya başladığımda doğrudan credential disclosure aramıyordum. İlk hedefim Kontrol Panel ile ERP istemcisi arasındaki TCP/3055 trafiğini anlamak, paket formatını çıkarmak ve login akışının nerede doğrulandığını görmekti. İlk bakışta authentication tarafı düzgün görünüyordu. `USERNAME` ve `PASSWORD` parse ediliyor, kullanıcı `PERSONEL` tablosunda aranıyor ve geçersiz kullanıcı için hata üretiliyordu. Sorun tam burada değildi. Geçersiz kullanıcı için hata üretildikten sonra fonksiyon dönmüyordu. Akış ortak response builder'a devam ediyor, bu builder da sunucunun kendi veritabanı bağlantısında kullandığı `SERVER_USERNAME` ve `SERVER_PASSWORD` alanlarını cevaba ekliyordu. `SERVER_ERROR` ise bundan sonra aynı cevaba yazılıyordu. Sonuç olarak sunucu şu iki şeyi aynı anda söylüyordu: ```text Kullanıcı adı veya parola yanlış. SERVER_USERNAME=<database user> SERVER_PASSWORD=<database password> ``` Bu davranışı önce yerel Firebird ortamında, ardından ayrı bir SQL Server kurulumunda doğruladım. Dönen credential'lar yalnızca yapılandırma artığı değildi: Firebird tarafında `SYSDBA`, SQL Server tarafında `sa` ve `sysadmin` yetkisiyle gerçek veritabanı oturumu açıldı. Birincil sınıflandırma: ```text CWE-200 — Exposure of Sensitive Information to an Unauthorized Actor ``` Destekleyici olarak: ```text CWE-522 — Insufficiently Protected Credentials CWE-306 — Missing Authentication for Critical Function ``` --- ## Test edilen ortamlar Bu yazıda yalnızca gerçekten doğruladığım kurulumları etkilenmiş kabul ediyorum. ### Yerel lab ```text Kontrol Panel: 26.02.25 ERP:           26.04.02 Backend:       Firebird Listener:      TCP/3055 Database:      SIRKET.FDB ``` `kontrolpanel.exe` SHA-256: ```text b27fc86175f203eb495d1134da67027adc2fa7728de58ea2428bce2ba93cdb5a ``` ### İkinci doğrulama ortamı Sunucunun kendi cevabında: ```text KP_VERSION=s26.02.19 SERVER_DBTYPE=1 ``` değerleri dönüyordu. Bu ortam SQL Server kullanıyordu. Hatalı login cevabında dönen kullanıcı `sa` idi ve aynı credential ile yapılan salt-okunur doğrulamada: ```text IS_SRVROLEMEMBER('sysadmin') = 1 ``` sonucu alındı. Başka sürümleri test etmediğim için etkilenen sürüm aralığını tahmin etmiyorum. --- ## 1. TCP/3055 protokolünü çıkarmak Kontrol Panel TCP/3055 üzerinde özel bir protokol kullanıyor. İlk iş olarak portu dinleyen `kontrolpanel.exe` ile bu porta bağlanan `werp.exe` binary'lerini karşılaştırdım. İki binary'de de aynı GUID biçimli sabit dikkatimi çekti. Değer hem ASCII hem UTF-16LE olarak bulunuyordu. Bu tek başına bunun bir crypto key olduğunu kanıtlamıyordu. Xref'leri takip ettiğimde aynı değerin TCP/3055 receive/send yolundaki crypto helper'lara aktarıldığını gördüm. Daha sonra canlı trafik üzerinde formatı çıkardım. Paket akışı: ```text Gönderim: cp1254 plaintext -> PKCS#7 padding, 64-bit block -> Blowfish ECB -> Base64 -> CRLF Alım: Base64 -> Blowfish ECB -> PKCS#7 unpad -> cp1254 plaintext ``` Her mesaj tek Base64 satırı olarak taşınıyor ve `\\r\\n` ile bitiyor. Bu modeli yalnız disassembly'ye bakarak kabul etmedim. Aynı formatla oluşturduğum `PING.` paketi çalışan Kontrol Panel tarafından kabul edildi; gelen cevap aynı codec ile anlamlı bir protokol mesajına çözüldü. Böylece paket formatını kendim üretebilir ve server response'larını bağımsız olarak parse edebilir hale geldim. --- ## 2. Login paketinin yapısı ERP tarafını takip ettiğimde login mesajında aşağıdaki alanların kullanıldığını gördüm: ```text USERNAME PASSWORD CLIENTID PROGRAM EXENAME EXEVERSIYON PATH ``` Burada özellikle geçerli hesap kullanmadım. Her denemede rastgele, var olmayan bir kullanıcı adı ve bilerek yanlış bir parola gönderdim: ```text USERNAME=mallory_invalid_<random> PASSWORD=INVALID ``` Beklediğim şey yalnızca authentication error almaktı. Gerçekten de sunucu girişi reddetti. Fakat çözülmüş cevapta şunlar birlikte bulunuyordu: ```text SERVER_ERROR=Kullanıcı adı veya parolası yanlış. SERVER_USERNAME=... SERVER_PASSWORD=... ``` İlk kritik nokta buydu. Dönen parola, gönderdiğim `PASSWORD=INVALID` değeri değildi. Kontrol Panel'in kendi veritabanı bağlantısında kullandığı credential'dı. --- ## 3. Binary üzerinde auth akışını takip etmek Runtime sonucu aldıktan sonra tekrar `kontrolpanel.exe` üzerine döndüm ve login branch'ini adres seviyesinde izledim. Gelen protokol verisi `0x01E1C1F0` civarında çözülüyor. `USERNAME` kontrolü: ```text 0x01E1C553 ``` Login credential yolu: ```text 0x01E1C7DA ``` Sunucu kullanıcıyı `PERSONEL` tablosunda arıyor. İlgili akış: ```text 0x01E1C821 0x01E1C843 ``` Mantık kabaca şu sorguya karşılık geliyor: ```sql SELECT * FROM PERSONEL WHERE AKTIF=1 AND USERNAME=<supplied username> ``` Rastgele kullanıcı adı için kayıt bulunmuyor. Bu durumda: ```text 0x01E1C84A ``` branch'i hata yoluna gidiyor ve: ```text 0x01E1C95C - 0x01E1C97A ``` aralığında authentication error hazırlanıyor. Buraya kadar davranış normal. Benim ilk analizimde de bu yüzden credential disclosure ihtimalini bir noktada false positive olarak elemiştim. Authentication gerçekten yapılıyordu. Daha sonra hatayı fark ettim: **authentication failure response üretimini durdurmuyordu.** --- ## 4. Asıl bug: ortak response builder Hata oluşturulduktan sonra fonksiyon return etmiyor. Akış: ```text 0x01E1D092 ``` civarındaki ortak response oluşturma bölümüne devam ediyor. Burada sunucu tarafındaki yapılandırılmış DB kullanıcı adı: ```text 0x01E1D0D6 - 0x01E1D0E3 ``` aralığında: ```text SERVER_USERNAME= ``` alanına ekleniyor. Hemen ardından parola: ```text 0x01E1D0E8 - 0x01E1D0F2 ``` aralığında: ```text SERVER_PASSWORD= ``` alanına ekleniyor. Authentication error ise **daha sonra**: ```text 0x01E1D28E - 0x01E1D293 ``` aralığında `SERVER_ERROR` olarak aynı response'a yazılıyor. Son cevap: ```text 0x01E1E00B - 0x01E1E0C1 ``` yolunda şifrelenip aynı TCP socket'e gönderiliyor. Problem tam olarak burada. Kodun mantığı özetlenirse: ```text invalid username/password | v authentication fails | v SERVER_ERROR hazırlanır | v ortak response builder devam eder | +--> SERVER_USERNAME eklenir | +--> SERVER_PASSWORD eklenir | +--> SERVER_ERROR eklenir | v response encrypt edilir | v aynı unauthenticated client'a gönderilir ``` Yani authentication kontrolü var, fakat secret'ların response'a eklenmesi authentication sonucuna bağlı değil. --- ## 5. Runtime doğrulama Yerel lab'da her test için yeni, var olmayan bir kullanıcı adı oluşturdum. Örnek: ```text CODEX_INVALID_a8a81a9a6b70 ``` Sunucu cevabında: ```text SERVER_ERROR=Kullanıcı adı veya parolası yanlış. ``` bulunuyordu. Aynı response içinde: ```text SERVER_USERNAME SERVER_PASSWORD ``` alanları da doluydu. Yerel Firebird ortamında kullanıcı adı: ```text SYSDBA ``` olarak döndü. Parolayı rapor artefact'larına yazmadan yalnız process memory içinde kullandım ve TCP üzerinden gerçek Firebird database'e salt-okunur bir doğrulama yaptım: ```sql SELECT CURRENT_USER FROM RDB$DATABASE; ``` Sonuç: ```text SYSDBA ``` Bu testin önemi şu: dönen değerlerin dummy config, eski credential veya kullanılmayan bir string olmadığını gösteriyor. Gerçek çalışan database administrator credential'ıydı. --- ## 6. İkinci ortam: SQL Server Aynı bug ayrı bir kurulumda tekrar doğrulandı. Bu kez response: ```text SERVER_DBTYPE=1 ``` döndürdüğü için backend'in SQL Server olduğunu anladım. Hatalı login cevabında: ```text SERVER_USERNAME=sa SERVER_PASSWORD=<non-empty> ``` alanları bulunuyordu. Dönen secret'ı yazdırmadan SQL Server'a bağlanıp yalnızca aşağıdaki salt-okunur kontrolleri yaptım: ```sql SELECT SYSTEM_USER, SUSER_SNAME(), IS_SRVROLEMEMBER('sysadmin'), DB_NAME(); ``` Sonuç: ```text SYSTEM_USER = sa SUSER_SNAME() = sa IS_SRVROLEMEMBER('sysadmin') = 1 DB_NAME() = WOLVOX9_SIRKET ``` Böylece bulgu iki farklı database backend üzerinde doğrulanmış oldu: ```text Firebird   -> SYSDBA SQL Server -> sa / sysadmin ``` Her iki doğrulamada da veri değiştiren veya silen SQL çalıştırılmadı. --- ## 7. Saldırı için ne gerekiyor? Credential disclosure kısmı için saldırganın ihtiyacı olan şey geçerli bir Wolvox hesabı değil. Başlangıç koşulu: ```text TCP/3055'e ağ erişimi ``` yeterli. Geçerli kullanıcı adı gerekmiyor. Geçerli parola gerekmiyor. Database credential'ını tahmin etmek gerekmiyor. Akış: ```text TCP/3055'e bağlan | v biçimsel olarak geçerli login paketi gönder | +--> USERNAME = var olmayan rastgele kullanıcı | +--> PASSWORD = yanlış değer | v sunucu login'i reddeder | v aynı response içinde DB credential döner ``` Dönen credential ile ayrıca database'e bağlanabilmek için Firebird/SQL Server portunun saldırgan açısından erişilebilir olması gerekir. Fakat **credential'ın TCP/3055 response'unda ifşa edilmesi için database portunun açık olması gerekmez.** --- ## 8. Neden bu auth bypass değil? Burada ince bir fark var. Wolvox login'i gerçekten başarısız oluyor. Yani saldırgan normal ERP kullanıcısı olarak authenticate edilmiyor. Bu nedenle bulguyu doğrudan \"authentication bypass\" diye adlandırmak doğru değil. Asıl problem: > Başarısız authentication response'una sunucu tarafındaki hassas credential'ın eklenmesi. Bu yüzden birincil CWE olarak: ```text CWE-200 ``` kullanıyorum. `CWE-306` root cause tarafında yardımcı bir sınıflandırma olabilir; `CWE-522` ise credential'ın istemciye bu biçimde taşınmasını tanımlamak için anlamlı. --- ## 9. Etki Doğrudan kanıtlanan etki: ```text Unauthenticated remote disclosure of configured database administrator credentials ``` Yerel ortamda dönen credential ile: ```text Firebird SYSDBA ``` oturumu açıldı. İkinci ortamda: ```text SQL Server sa sysadmin = 1 ``` doğrulandı. Bu nedenle bulgu yalnızca \"username/password string'i görülebiliyor\" seviyesinde değil. Ifşa edilen bilgiler gerçek ve aktif administrator credential'larıydı. Araştırma sırasında yıkıcı etki üretmedim. Database üzerinde veri değiştirme, silme, servis durdurma veya işletim sistemi seviyesinde execution denenmedi. Raporda kullandığım geçici CVSS v3.1: ```text CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H ``` Score: ```text 9.8 ``` Buradaki `I:H` ve `A:H`, iki backend üzerinde doğrulanan `SYSDBA` / `sysadmin` otoritesinden geliyor; araştırma sırasında veri silindiği anlamına gelmiyor. --- ## 10. Protokol şifrelemesi neden koruma sağlamıyor? TCP/3055 mesajları plaintext gitmiyor. Fakat istemci ve sunucu binary'lerinde aynı statik Blowfish key materyali bulunuyor. Protokolü tersine mühendislik ettikten sonra bağımsız bir istemci: ```text packet oluşturabiliyor response decrypt edebiliyor ``` Bu nedenle custom encryption authentication boundary olarak kabul edilemez. Buradaki asıl vulnerability yine crypto değil. Crypto tamamen sağlam olsaydı bile sunucunun başarısız login response'una DB password eklemesi mantıksal olarak yanlış olurdu. Statik key yalnızca bu response'u bağımsız bir client'ın okuyabilmesini kolaylaştırıyor. --- ## 11. Güvenli PoC mantığı Kullandığım dağıtılabilir PoC'nin amacı password'ü ekrana basmak değildi. Mantığı şu kadar: ```python username = random_nonexistent_username() password = \"INVALID\" response = send_invalid_login(username, password) assert response[\"SERVER_ERROR\"] assert response[\"SERVER_USERNAME\"] assert response[\"SERVER_PASSWORD\"] print(\"credential disclosure confirmed\") ``` PoC rapor çıktısında yalnızca: ```text returned_db_username returned_db_password_present returned_db_password_length authentication_error_present ``` gibi alanları tutuyordu. Plaintext password artefact'a yazılmadı. Database doğrulaması seçildiğinde secret yalnız process memory içinde kullanıldı ve salt-okunur kimlik/rol sorgusu çalıştırıldı. --- ## 12. Root cause Bence root cause tek cümlede şu: > Authentication failure state'i response serialization aşamasında hassas alanların eklenmesini engellemiyor. Başarısız login için ideal akış: ```text auth failed -> generic error -> send -> return ``` Mevcut akış: ```text auth failed -> error hazırlanır -> common response builder -> DB username eklenir -> DB password eklenir -> error eklenir -> send ``` Bug burada. --- ## 13. Düzeltme En küçük düzeltme bile başarısız login ile başarı response'unu kesin olarak ayırmalı. `SERVER_ERROR` doluysa veya kullanıcı/parola kontrolü başarısızsa: ```text SERVER_USERNAME SERVER_PASSWORD DB_INSTANCE SERVER_DBPATH database alias bilgileri ``` response'a hiç eklenmemeli. Daha doğru tasarım ise database administrator credential'ını istemci protokolünden tamamen kaldırmak. ERP istemcisinin gerçekten DB işlemi yapması gerekiyorsa bunu: ```text authenticated application API ``` üzerinden yapması daha sağlıklı. Ayrıca: - uygulama bağlantısında `SYSDBA` / `sa` gibi full-admin hesaplar kullanılmamalı, - TCP/3055 yalnız gerekli ağ segmentlerinden erişilebilir olmalı, - database portları istemci ağlarına/İnternet'e açılmamalı, - ifşa olmuş olabilecek DB credential'ları rotate edilmeli, - statik Blowfish protokolü güncel authenticated transport ile değiştirilmelidir. --- ## Sonuç Bu bulguda en ilginç nokta authentication'ın tamamen yok olması değildi. Authentication gerçekten vardı ve geçersiz kullanıcıyı doğru şekilde reddediyordu. Problem, ret kararından **sonra** ortaya çıkıyordu. Sunucu bir taraftan: ```text Kullanıcı adı veya parolası yanlış. ``` derken aynı cevabın içine kendi database administrator kullanıcı adını ve parolasını da koyuyordu. Static analizde zincir: ```text invalid login -> PERSONEL lookup fails -> SERVER_ERROR prepared -> common response builder -> SERVER_USERNAME -> SERVER_PASSWORD -> SERVER_ERROR -> encrypted socket response ``` Runtime tarafında ise bunun gerçek credential olduğu iki ayrı backend ile doğrulandı: ```text Firebird   -> SYSDBA SQL Server -> sa / sysadmin ``` Benim için bulgunun esas değeri de burada: yalnızca bir secret string görmek değil, başarısız authentication'dan başlayıp gerçek administrator session'a kadar bütün zinciri kapatmak. --- ## Teknik özet ```text Product: AKINSOFT WOLVOX Component: Kontrol Panel / TCP 3055 Confirmed versions: Kontrol Panel 26.02.25 KP_VERSION=s26.02.19 olan ayrı kurulum Attack vector: Network Privileges required: None User interaction: None Trigger: Invalid / nonexistent WOLVOX login Leaked fields: SERVER_USERNAME SERVER_PASSWORD Validated backends: Firebird -> SYSDBA Microsoft SQL Server -> sa / sysadmin Primary CWE: CWE-200 Supporting CWE: CWE-522 CWE-306 Provisional CVSS v3.1: 9.8 Vector: CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H ```"
